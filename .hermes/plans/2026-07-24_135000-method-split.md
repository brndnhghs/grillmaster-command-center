# Method File Split Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. This plan covers converting 5 monolithic method files into 5 subdirectory packages, each with one file per method.

**Goal:** Isolate every `@method` node into its own Python file so library authoring is easier — each method is self-contained, independently editable, and discoverable by filename.

**Architecture:** Move 4 monolithic top-level `.py` files into subdirectory packages following the existing pattern (`filters/`, `patterns/`, `simulations/`, etc.) where each file holds exactly one `@method` function. For `gpu_shaders.py`, move the factory infrastructure and shader lists into a subdirectory while keeping the loop-generated registration pattern (since expanding 159 closures into individual files would be pure mechanical noise with no authoring benefit).

**Tech Stack:** Python 3.11, existing `pkgutil`-based auto-discovery in `__init__.py`, existing `@method` decorator in `core/registry.py`.

**Total scope:** 29 individual method files from 4 monolithic files + 159 loop-generated methods moved to a subdirectory package.

### Phase 6: Convert `gpu_shaders.py` to subdirectory package

`gpu_shaders.py` uses a **different architectural pattern** — 3 factory functions (`_make_proc`, `_make_filt`, `_make_typed`) are called in module-level loops over 3 shader lists (`_PROC_SHADERS` (27), `_FILT_SHADERS` (22), `_TYPED_SHADER_NODES` (109)) to generate 159 methods at import time, plus 1 explicit `@method` for the legacy combined node.

Expanding this into 159 individual files would be mechanical noise with no authoring benefit — every file would be practically identical. The factory pattern is the *right* abstraction here: it avoids 155× repetition of the same `@method(id=..., name=..., ...)` boilerplate. Instead, we move **the entire factory infrastructure** into `gpu_shaders/_shared.py`.

#### Task 6.1: Create `gpu_shaders/_shared.py`

**Objective:** Move the factory functions, shader lists, param templates, and registration loops into a single shared module.

**Files:**
- Create: `image_pipeline/methods/gpu_shaders/_shared.py`

**What goes in:**

## Risks, Tradeoffs, and Open Questions

### Risks

1. **Import path regression** — The biggest risk. Every file changes `from ..core.X` to `from ...core.X`. A single wrong dot causes `ImportError` at registration time, which means ALL methods fail to register (because `methods/__init__.py` fails to import the subdir). **Mitigation:** verify each file independently before deleting the monolithic.

2. **`gpu_shaders.py` registration loop timing** — The 3 module-level loops at the bottom of `gpu_shaders.py` fire on import. When moved to `_shared.py`, they fire when `_shared.py` is imported, which is triggered by the `__init__.py` auto-discover loop. This should work identically, but the `GPU_SHADER_NODE_MAP` and `CLIENT_GPU_SHIMS` dicts must be defined in `_shared.py` too (they're populated by the same loops).

3. **Module-level side effects in `gpu_shaders.py`** — The `GPU_SHADER_NODE_MAP` and `SHADER_NAMES` dicts are populated at module level and may be imported by other modules (e.g., `ui/`, `server.py`). Check if anything imports from `gpu_shaders` by name:
   ```
   grep -rn 'from.*gpu_shaders\|import.*gpu_shaders' image_pipeline/ --include='*.py'
   ```
   If other modules import specific names (e.g., `from image_pipeline.methods.gpu_shaders import GPU_SHADER_NODE_MAP`), those imports need updating to `from image_pipeline.methods.gpu_shaders._shared import GPU_SHADER_NODE_MAP`.

### Tradeoffs

1. **gpu_shaders.py kept as factories** — The 159 loop-generated methods remain in a factory pattern rather than 159 individual files. This means a developer adding a new GPU shader adds a tuple to `_TYPED_SHADER_NODES` in `_shared.py` rather than creating a new file. That's a different authoring model than hand-authored nodes. **Decision:** Accept this — the factory is the right abstraction for 159 nearly-identical closure nodes. Adding a new file per shader would be 30× more boilerplate with zero gain.

2. **Duplicate imports across individual files** — Each of the 29 individual method files carries its own import block. For methods that share imports (e.g., all `channels/` files import `math`, `random`, `numpy`, `seed_all`), this is a repetition of ~6 import lines per file. **Decision:** Accept this — it's standard Python practice, keeps each file self-contained, and avoids cross-file coupling.

### Open Questions

1. **Check `gpu_shaders.py` external imports** — Before starting Phase 6, grep for external references to `gpu_shaders`:
   ```
   grep -rn 'gpu_shaders' image_pipeline/ --include='*.py' | grep -v 'methods/gpu_shaders'
   ```
   If anything imports `GPU_SHADER_NODE_MAP` or `CLIENT_GPU_SHIMS` from `gpu_shaders`, those imports need updating to `gpu_shaders._shared`. This is a pre-flight check for Phase 6.

2. **Codegen `simulations.py`** — `codegen/simulations.py` has 1 method (line 221). It's already in the `codegen/` subdir with a single method. No split needed.
